\label{cap:marco-teorico}
En este capítulo se presentan los fundamentos conceptuales que sustentan el desarrollo del presente proyecto de grado. Se revisan los principales enfoques teóricos, definiciones, características y elementos relevantes del área de conocimiento involucrada, con el fin de establecer una base sólida para la comprensión del problema planteado y de las soluciones propuestas.

\section{Fundamentos de Modelado Conceptual y Notaciones de Diseño}
\label{sec:modelado-conceptual}

\subsection{Evolución y Limitaciones del Modelado Entidad-Relación Tradicional}
\label{subsec:evolucion-er}

El diseño de bases de datos relacionales encuentra sus cimientos en el modelo Entidad-Relación clásico propuesto originalmente por Peter Chen \cite{chen1976entity}. Si bien este formalismo provee una abstracción matemática sólida para identificar entidades, atributos y relaciones binarias, presenta limitaciones expresivas cuando se enfrenta a dominios de software complejos que requieren patrones estructurales recurrentes (como jerarquías de herencia, composiciones estrictas o relaciones reflexivas históricas).

Para mitigar estas deficiencias en entornos de desarrollo modernos, se emplean notaciones gráficas normalizadas como la notación de Patas de Gallo (\textit{Crow's Foot Notation}), la cual permite acotar con precisión las cardinalidades (mínima y máxima) y las dependencias de existencia entre entidades. Sin embargo, la representación gráfica por sí sola no garantiza una traducción directa o automatizada hacia el código fuente de los frameworks de persistencia actuales.

\subsection{La Brecha de Impedancia y el Mapeo Objeto-Relacional (ORM)}
\label{subsec:brecha-impedancia}

Un desafío fundamental en la ingeniería de software es la denominada \textit{brecha de impedancia objeto-relacional} (\textit{Object-Relational Impedance Mismatch}), la cual surge de las diferencias estructurales y paradigmáticas entre los sistemas de gestión de bases de datos relacionales (basados en tablas, tuplas y relaciones matemáticas) y los lenguajes de programación orientados a objetos (basados en clases, herencia y referencias en memoria).

Para resolver esta discrepancia sin recurrir masivamente a consultas SQL escritas a mano, se utilizan las herramientas de Mapeo Objeto-Relacional (\textit{ORM}). En el ecosistema de Python, \textit{Django ORM} actúa como una capa de abstracción que traduce las clases declaradas en código fuente hacia esquemas relacionales ejecutables en SGBD como PostgreSQL. No obstante, la construcción manual de estos modelos orientados a objetos a partir de diagramas conceptuales complejos es una tarea propensa a errores humanos y desalineaciones arquitectónicas, lo que motiva la necesidad de automatizar este proceso mediante gramáticas formales.

\section{Idioms en el modelo conceptual}
\label{sec:idioms-modelo-conceptual}

\subsection{Definición}
\label{subsec:idioms-definicion}

El lenguaje \textit{Idioms} proporciona diferentes construcciones orientadas a representar patrones recurrentes presentes en el modelado conceptual de un dominio. Estas construcciones, denominadas \textit{Idioms}, fueron formalizadas por M. Flores \cite{flores2006idioms} y permiten expresar relaciones y estructuras semánticas de manera específica, facilitando la representación de situaciones que aparecen con frecuencia durante el diseño de modelos de datos.

\subsection{Características}
\label{subsec:idioms-caracteristicas}

Los Idioms presentan un conjunto de características que permiten utilizarlos como construcciones específicas dentro del modelado conceptual. Entre las principales se encuentran las siguientes:

\begin{itemize}
    \item \textbf{Representación de patrones recurrentes:} permiten expresar estructuras y relaciones que aparecen de manera frecuente en diferentes dominios de modelado.
    \item \textbf{Orientación semántica:} cada Idiom representa una situación conceptual determinada, permitiendo expresar de manera explícita el significado de las relaciones existentes entre los elementos del modelo.
    \item \textbf{Estructura definida:} cada Idiom establece una forma particular de relacionar entidades y roles, de acuerdo con el patrón que representa.
    \item \textbf{Reutilización:} los mismos patrones pueden emplearse en diferentes modelos y dominios cuando presentan una estructura conceptual similar.
    \item \textbf{Extensibilidad del modelo:} los Idioms permiten representar situaciones que pueden evolucionar o incorporar nuevos elementos sin modificar necesariamente la estructura general del patrón utilizado.
\end{itemize}

\subsection{Elementos}
\label{subsec: idioms-elementos}

A continuación, se presentan los principales Idioms considerados en el desarrollo del proyecto, describiendo su propósito y las características que los diferencian dentro del modelado conceptual. Estos Idioms constituyen, además, parte de las construcciones consideradas posteriormente durante el procesamiento de los modelos definidos mediante el lenguaje.

\subsubsection{Clasificación o Catálogo}
El Idiom de clasificación o catálogo permite representar una relación en la que una entidad es asociada con un conjunto de valores o entidades que actúan como sus clasificadores. Este patrón aparece de manera frecuente en los modelos conceptuales, debido a que permite representar características de una entidad mediante valores definidos dentro de un conjunto que puede ser ampliado.

En este tipo de relación intervienen dos roles principales: la entidad clasificada, que corresponde al elemento al cual se asigna una clasificación, y la entidad clasificadora, que contiene los valores utilizados para establecer dicha clasificación. Por ejemplo, una entidad “Persona” puede estar relacionada con una entidad “Ciudad” mediante el atributo o rol “nacionalidad”, de manera que una instancia de Persona pueda asociarse con una instancia determinada de Ciudad.

Una de las características de este Idiom es que el conjunto de clasificadores puede crecer conforme evoluciona el dominio. Por ejemplo, pueden incorporarse nuevas ciudades sin modificar la estructura de la entidad que utiliza dicho catálogo. Asimismo, un mismo catálogo puede ser utilizado para clasificar diferentes entidades cuando el dominio así lo requiere.

La utilización de este Idiom permite representar explícitamente la relación semántica entre una entidad y los valores que pueden clasificarla, evitando incorporar directamente dichos valores como atributos independientes dentro de la entidad clasificada. De esta manera, la estructura del modelo puede mantener una separación entre los elementos que representan entidades del dominio y aquellos que funcionan como valores de clasificación.

\subsubsection{Composición}
El Idiom de composición permite representar una entidad como resultado de la combinación de otras entidades que participan en su conformación. Este patrón proporciona una forma estructurada de expresar relaciones en las que varios elementos del dominio intervienen conjuntamente para representar una entidad o concepto compuesto.

A diferencia de representar directamente estas situaciones mediante una relación genérica entre entidades, el Idiom de composición permite identificar de manera explícita cuáles son los elementos que participan en la formación del elemento compuesto. De esta manera, la estructura del modelo refleja con mayor claridad la dependencia conceptual existente entre sus componentes.

Una característica de este Idiom es que no establece una cantidad fija de entidades participantes. Una composición puede involucrar dos o más entidades, dependiendo de las características del dominio que se desea representar. Esto permite utilizar el mismo patrón en diferentes escenarios y con distintos niveles de complejidad.

Asimismo, la composición puede utilizarse para representar diferentes configuraciones de un mismo concepto compuesto. Cuando el dominio requiere considerar cambios o variantes a lo largo del tiempo, es posible asociar información temporal al elemento resultante, permitiendo distinguir diferentes versiones o estados de la composición.

\subsubsection{Maestro-Detalle}
El Idiom de Maestro-Detalle permite representar situaciones en las que una entidad principal mantiene una relación con una o varias entidades dependientes. En este patrón, la entidad maestra representa el elemento principal del modelo, mientras que las entidades de detalle contienen información asociada cuya existencia se encuentra vinculada al elemento principal.

Este Idiom resulta útil cuando una determinada característica del dominio puede presentarse mediante múltiples elementos asociados a una misma entidad. En lugar de representar estos valores directamente como atributos con múltiples ocurrencias, el patrón permite modelarlos mediante una estructura independiente relacionada con la entidad maestra.

Una de sus principales características es la posibilidad de representar una cantidad variable de elementos de detalle asociados a una misma entidad maestra. Esto permite modelar situaciones en las que el número de elementos relacionados puede aumentar o disminuir de acuerdo con las necesidades del dominio, sin requerir modificaciones en la estructura de la entidad principal.

La separación entre la entidad maestra y sus elementos de detalle también contribuye a mantener una estructura más organizada del modelo conceptual. Los datos correspondientes al elemento principal permanecen diferenciados de aquellos que representan información dependiente, facilitando la interpretación de la relación entre ambos tipos de entidades.

En este sentido, el Idiom de Maestro-Detalle constituye un patrón útil para representar estructuras en las que una entidad principal puede estar asociada con múltiples elementos dependientes, manteniendo explícita la relación existente entre ellos.

\subsubsection{Reflexivo}
El Idiom Reflexivo permite representar situaciones en las que una entidad puede establecer relaciones con otras entidades del mismo tipo. En este patrón, una misma clase de entidad puede participar en diferentes roles dentro de una relación, permitiendo representar estructuras en las que los elementos relacionados pertenecen al mismo conjunto de entidades.

Este Idiom resulta especialmente apropiado para representar estructuras jerárquicas o relaciones de dependencia. Por ejemplo, en un dominio organizacional, una entidad “Empleado” puede relacionarse con otra instancia de la misma entidad para representar la relación existente entre un empleado y su supervisor. De manera similar, puede utilizarse para representar estructuras como categorías y subcategorías, donde una categoría puede depender o estar relacionada con otra categoría del mismo tipo.

Una característica importante del Idiom Reflexivo es que los roles que participan en la relación permiten diferenciar la función que cumple cada instancia dentro del vínculo. De esta manera, aunque los elementos involucrados pertenecen al mismo tipo de entidad, la relación puede expresar una diferencia semántica entre ellos.

Este patrón permite representar estructuras que requieren relaciones entre elementos de una misma entidad sin necesidad de introducir una entidad adicional únicamente para expresar el vínculo. Por ello, resulta útil en dominios donde existen relaciones jerárquicas, dependencias o asociaciones entre elementos que pertenecen a un mismo conjunto.

\subsubsection{Reflexivo con historia}
El Idiom Reflexivo con historia extiende el patrón Reflexivo mediante la incorporación de información histórica asociada a las relaciones entre entidades. Mientras que el Reflexivo permite representar una relación entre elementos que pertenecen al mismo tipo de entidad, esta variante permite además conservar los cambios que dicha relación experimenta a lo largo del tiempo.

Para representar esta información, el Idiom incorpora una entidad encargada de almacenar los registros históricos de la relación. De esta manera, los cambios que se producen en el vínculo entre las entidades pueden conservarse como parte del modelo, en lugar de mantener únicamente el estado actual de la relación.

Este patrón resulta útil en dominios donde el historial de una relación constituye información relevante. Por ejemplo, puede utilizarse para registrar la evolución de relaciones laborales, cambios de responsabilidad dentro de una organización o diferentes estados que haya presentado una relación entre entidades a lo largo del tiempo.

La incorporación del componente histórico permite diferenciar entre el estado vigente de una relación y los estados que esta presentó anteriormente. Esto proporciona una representación más completa del dominio cuando resulta necesario consultar o conservar información relacionada con la evolución temporal de los vínculos entre entidades.

En consecuencia, el Idiom Reflexivo con historia permite combinar la capacidad del patrón Reflexivo para representar relaciones entre elementos del mismo tipo con un mecanismo orientado a preservar el historial de dichas relaciones.

\subsubsection{IS-A o Generalización}
El Idiom IS-A o Generalización permite representar relaciones jerárquicas entre tipos de entidades, estableciendo una relación entre un concepto general y uno o varios conceptos que representan especializaciones del mismo.

En este patrón, una entidad general representa las características o propiedades comunes de un conjunto de entidades más específicas. Las entidades especializadas, por su parte, permiten representar categorías particulares del concepto general. De esta manera, el modelo puede expresar que un determinado tipo de entidad constituye una especialización de otro tipo más general.

Una de las características de este Idiom es que permite representar estructuras de generalización con diferentes niveles de especialización. Una misma entidad general puede estar asociada con múltiples entidades especializadas, permitiendo representar diferentes categorías dentro de un mismo concepto. Asimismo, un modelo puede establecer relaciones de especialización entre distintos tipos de entidades cuando las características del dominio así lo requieran.

Este patrón permite expresar diferencias conceptuales entre tipos de entidades sin limitar el modelo a una única estructura de clasificación. Por ejemplo, una entidad “Vehículo” puede representar un concepto general, mientras que “Automóvil” y “Motocicleta” pueden constituir especializaciones de dicho concepto.

\section{Plataforma de desarrollo}
\label{subsec:plataforma-desarrollo}

\subsection{Definición}
\label{subsubsec:plataforma-definicion}

La Plataforma de Desarrollo se define como el entorno integrado de hardware y software que proporciona el conjunto de herramientas, marcos de trabajo (\textit{frameworks}), librerías y lenguajes necesarios para diseñar, construir, probar y desplegar la solución tecnológica propuesta. En el contexto de este proyecto, la plataforma se centra en el lado del servidor (\textit{backend}) y la capa de \textit{Machine Learning}, ya que la interfaz de usuario (\textit{frontend}) es provista por la arquitectura existente (el diagramador basado en \textit{Idioms}).

\subsection{Características}
\label{subsubsec:plataforma-caracteristicas}

Las características de la plataforma deben enfocarse en cómo las tecnologías seleccionadas dan soporte a los requerimientos clave del proyecto: Generación de Código y Abstracción de Base de Datos.

\paragraph{A. Lenguaje de Programación (Python)}
Se selecciona Python por su claridad sintáctica y su ecosistema avanzado para el desarrollo \textit{backend} y la inteligencia artificial.

\begin{itemize}
    \item \textbf{Legibilidad y Mantenibilidad:} Su sintaxis simple facilita la implementación y el mantenimiento de algoritmos complejos, como el que realizará la Gramática Simple para convertir los \textit{Tokens} de la IA a código Django.
    \item \textbf{Ecosistema de ML/DL:} Proporciona un soporte inigualable para la capa de IA a través de librerías como PyTorch o TensorFlow y el ecosistema Hugging Face para la implementación de CodeT5.
\end{itemize}

\paragraph{B. Framework de Desarrollo (Django)}
Django es el \textit{framework} web de alto nivel elegido porque es el destino final del código generado por el módulo. Su Mapeo Objeto-Relacional (ORM) es una de sus características más potentes. Elegir Django como plataforma de desarrollo y como \textit{output} final garantiza que el código generado sea coherente y fácil de integrar en el ecosistema dominante de Python.

\paragraph{C. Componentes de Inteligencia Artificial (CodeT5)}
Se incorpora la infraestructura necesaria para la generación automatizada de la capa de persistencia se empleó el modelo CodeT5, una arquitectura basada en codificador-decodificador preentrenada con consciencia de identificadores para tareas de ingeniería de software \cite{wang2021codet5}.

\begin{itemize}
    \item \textbf{Librerías de Transformación:} Uso de la librería Hugging Face \texttt{transformers} para cargar el modelo CodeT5. Esta librería estandariza la interacción con modelos de \textit{Deep Learning} de código abierto.
    \item \textbf{Procesamiento de Tensores:} Utilización del \textit{framework} PyTorch o TensorFlow como \textit{backend} para ejecutar las operaciones matemáticas necesarias para la inferencia y el ajuste fino (\textit{fine-tuning}) del modelo CodeT5 en el entorno local.
\end{itemize}

\subsection{Herramientas}
\label{subsubsec:plataforma-herramientas}

Este apartado describe las herramientas de software de apoyo que son fundamentales para la construcción, el control de calidad, el análisis de la estructura de entrada y la gestión colaborativa del código.

\paragraph{ANTLR (ANother Tool for Language Recognition)}
ANTLR es un generador de \textit{parsers} de código abierto, diseñado para construir analizadores léxicos (\textit{lexers}), sintácticos (\textit{parsers}) y recorredores de árboles (\textit{tree-walkers}) a partir de una gramática formal \cite{parr2013definitive}. En el ámbito de la ingeniería de software, esta herramienta se utiliza para procesar Lenguajes Específicos de Dominio (\textit{DSLs}), transformando representaciones textuales o visuales abstractas en estructuras de datos procesables \cite{fowler2010dsl}. 

En la presente arquitectura, ANTLR cumple el rol crítico de procesar la gramática de \textit{Idioms} y construir el Árbol Sintáctico Abstracto (\textit{AST}), asegurando que la entrada estructurada que recibe el modelo de inteligencia artificial cumpla rigurosamente con las reglas formales del modelado conceptual antes de la traducción de código.
ANTLR es la tecnología que procesa la Gramática de \textit{Idioms} y genera el Árbol Sintáctico de Entrada. Es crucial porque valida sintácticamente el diagrama Entidad-Relación, asegurando que el \textit{input} que recibe CodeT5 sea una estructura de datos formalmente correcta, lo que es un pre-requisito para cualquier traducción determinista.

\paragraph{Sistema de Control de Versiones (Git)}
Git es un sistema de control de versiones distribuido que rastrea los cambios en el código fuente durante el desarrollo. Permite gestionar las múltiples iteraciones del proyecto, facilitando la colaboración (si es necesaria) y asegurando un historial de cambios.

\paragraph{Entorno de Desarrollo Integrado (IDE) y Entorno Virtual}
Se utilizan herramientas específicas para facilitar la codificación en Python y la gestión de dependencias complejas. Los IDEs de Python (ej., VS Code o PyCharm) proveen capacidades avanzadas de depuración, autocompletado y análisis de código estático, críticos para trabajar con \textit{frameworks} complejos como Django y librerías de \textit{Deep Learning} como PyTorch. Se combina con entornos virtuales (ej., \texttt{venv} o \texttt{conda}) que aíslan las dependencias del proyecto (incluyendo las versiones específicas) para evitar conflictos con otros proyectos del sistema.
